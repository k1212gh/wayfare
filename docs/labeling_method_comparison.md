# 화면 라벨링 방식 비교 — "후보 선택"은 검증된 방식인가? (2026-09-13)

질문: 지금 Stage 5 기본인 **후보 선택**(화면에 보이는 텍스트 중 번호 하나를 고르게 하기)이 알려진 방식인지,
그리고 다른 방식(자유 생성, 스크린샷 사용)과 정확도가 얼마나 다른지.

## 1. 문헌에서의 위치 — 결론부터

- "후보 선택"이라는 이름의 **화면 이름 짓기 전용 논문은 없다.** 우리 방식은 아래 두 갈래의 알려진 아이디어를 화면 명명에 적용한 것이다.
  1. **추출형(extractive) vs 생성형(abstractive)** — 근거 텍스트가 있을 때 답을 그 안에서 고르게 하면 환각이 드물고,
     근거 없이 지어내게 하면 환각이 잦다는 것은 LLM 환각 연구에서 반복 확인된 사실이다
     ([Frontiers in AI 2025 환각 서베이](https://www.frontiersin.org/journals/artificial-intelligence/articles/10.3389/frai.2025.1622292/full)).
  2. **번호 붙인 후보에서 고르기(candidate selection)** 는 GUI 에이전트의 표준 grounding 기법이다 —
     [Set-of-Mark](https://arxiv.org/abs/2310.11441)(이미지에 번호 마크를 얹고 번호로 답하게 함),
     [SeeAct](https://arxiv.org/abs/2401.01614)("Grounding via Textual Choices": 요소 텍스트 후보 목록에서 고르기).
     다만 이들은 **누를 요소**를 고르는 문제이지 **화면 이름**을 정하는 문제가 아니다.
- 화면 이름/요약의 학계 표준은 오히려 **생성형**이다 — [Screen2Words](https://arxiv.org/abs/2108.03353)(UIST 2021)는
  스크린샷 + 뷰 계층 + 텍스트를 넣고 요약문을 *생성*했고, 이후 [Spotlight](https://openreview.net/pdf?id=9yE2xEj0BH7)(ICLR 2023) 등도 생성형이다.
- 즉 "후보 선택"은 **검증된 원리(추출형 grounding)의 합리적 응용이지 그 자체로 검증된 방식은 아니다.** 그래서 아래 실험으로 직접 쟀다.

## 2. 실험 설계

| 항목 | 값 |
|---|---|
| 화면 | 투어 `358002fe`(메가커피 재탐색) page 노드 34개 — 정답표 `docs/bench_gold_megacoffee_358002fe.json` (수작업, 실제 제목 텍스트 `label_gold`) |
| 모델 | gemma4:12b, qwen3.5:9b, qwen2.5:7b-instruct(+qwen2.5vl:7b 비전) — Ollama 네이티브, temperature 0.1 |
| 스크립트 | `scripts/bench_label_methods.py` (원시 결과 `docs/labeling_method_comparison_raw_0913.md`) |

네 가지 방식 (입력 → 출력):

| 방식 | 입력 | 출력 |
|---|---|---|
| ① 후보 선택 (텍스트) — **현재 기본** | 화면 텍스트 후보 ≤8개 | 번호 (없으면 -1) |
| ② 자유 생성 (텍스트) | 같은 후보 | 라벨 문자열 ≤12자 |
| ③ 자유 생성 (스크린샷) | 스크린샷 1장 | 라벨 문자열 |
| ④ 후보 선택 (스크린샷+후보) | 스크린샷 + 후보 | 번호 |

**지표는 "최종 라벨 정확도"** — 노드가 실제로 갖게 되는 라벨이 정답 제목과 맞는가.
후보 선택에서 -1 이나 무응답이면 휴리스틱 라벨(후보 0번)이 그대로 남는데, 그것까지 포함해 채점한다(사용자가 그래프에서 보는 결과 기준).
strict = 실제 제목(+정답 번호의 후보 텍스트), lenient = 허용 후보까지. 공백 제거·소문자 후 포함 관계.

기준선 두 개:
- **LLM 없음(휴리스틱, 후보 0번 그대로)**: strict **65%** (22/34), lenient 74%.
- 후보 선택의 **상한**(후보 안에 정답이 있는 노드): 91% (31/34).

## 3. 결과 (최종 라벨 정확도, strict / lenient)

| 모델 | ① 후보 선택(텍스트) | ② 자유 생성(텍스트) | ③ 자유 생성(스크린샷) | ④ 후보 선택(스크린샷+후보) |
|---|---|---|---|---|
| gemma4:12b | 65% / 74% | 59% / 68% | **79% / 79%** | 71% / 74% |
| qwen3.5:9b | 62% / 71% | 62% / 71% | **82% / 85%** | 68% / 71% |
| qwen2.5:7b (+vl) | 65% / 74% | 50% / 59% | **74% / 76%** | 65% / 68% |
| (LLM 없음) | 65% / 74% | | | |

시간(34노드): 텍스트 방식 22~27초(배치 20), 스크린샷 방식 31~48초(0.9~1.4초/장 — 라벨만 물어서 짧음).

### 읽는 법
1. **텍스트만으로는 어떤 LLM 방식도 휴리스틱(65%)을 못 넘는다.** 후보 선택은 정확히 기준선과 같고(맞는 걸 고를 때 = 후보 0번,
   틀리면 오히려 손해), 자유 생성은 더 나쁘다(qwen2.5 50%). 텍스트 후보에는 화면의 *구조*(무엇이 헤더이고 무엇이 팝업인지)가 없기 때문이다.
   현재 기본 방식의 실제 기여는 라벨이 아니라 **분류(category)** 다.
2. **스크린샷을 보여주면 +14~20%p.** 오버레이(영수증·날짜 선택·조회조건·이벤트 공유)와 후보가 잡음인 화면(알림, 약관, 스탬프+배너)을
   자유 생성이 맞힌다 — 후보 목록에 아예 없던 제목("영수증", "알림", "날짜 선택")을 화면에서 읽어낸다.
3. **스크린샷이 있어도 "후보에서 고르게" 하면 오히려 떨어진다**(④ < ③, 8~14%p). 후보 목록이 제목을 담지 못한 12개 노드에서
   -1 → 휴리스틱 라벨로 되돌아가기 때문. 후보 제약이 이 데이터에선 상한(91%)보다 모델의 실수를 더 키운다.
4. **자유 생성의 환각은 있지만 작다.** ③의 오답 중 화면 텍스트에 없는 말을 지어낸 것은 gemma 4/34, qwen3.5 2/34("NCT 127 이벤트", "매가MGC커피"),
   qwen2.5vl 6/34. 그리고 ③의 라벨을 후보 텍스트에 스냅(포함 관계면 후보 원문으로 교체)해도 정확도는 그대로(27·28·25/34)다 —
   즉 **"스크린샷 자유 생성 + 후보로 근거화"** 가 정확도와 근거성을 동시에 가진다.
5. 세 모델·네 방식 모두 틀린 화면 2개: 주문내역 위 MY매장 확인창(83a1a0, 6221a8 — 모델은 "주문완료"라고 답함; 확인창이 화면을 덮어 헤더가
   안 보임)과 Google Play 페이지(ba0459). 이건 방식이 아니라 데이터(오버레이가 헤더를 가림) 문제다.

## 4. 결론과 권장

- "후보 선택"은 **원리는 검증됐지만(추출형 grounding), 화면 이름 짓기에서는 텍스트만으로 이득이 없다.** 이 앱에서는 LLM 없는 휴리스틱과 동률.
- 정확도가 우선이면 Stage 5 라벨은 **③ 스크린샷 자유 생성**으로 바꾸고, 생성된 라벨이 화면 텍스트 후보와 겹치면 후보 원문으로 스냅해 근거를 남기는 것이
  가장 좋다(qwen3.5 82%, gemma4 79%). 비용은 화면당 1~1.4초(현재 비전 라벨러가 purpose/description 까지 뽑느라 4~5초 걸리는 것보다 싸다).
- 텍스트 후보 선택은 **비전 모델이 없는 환경의 대체 경로**와 **category 분류**용으로만 남긴다.
- 방식과 무관한 개선: Stage 4 후보 추출에서 아이콘 설명("화살표 아이콘")·알림 배너("이름/톤")·외부 앱 잔재를 걸러야 하고,
  오버레이가 헤더를 가릴 때는 그 아래 화면의 제목(부모 노드 라벨)을 후보로 넣어야 한다.
