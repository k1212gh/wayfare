각 앱 내 정책의 Marginal Contribution

지표 의미 — 각 정책의 압축률에서 L1_only 압축률을 뺀 값. "이 정책이 L1 단독 대비 얼마나 더 머지하는가" = 그 정책 추가 신호의 진짜 기여도. 두 앱에서 같은 marginal 값 (∆ < 5%p) = robust, 다른 방향이거나 큰 차이 = 데이터 의존.

해석 — L2/L3 의 marginal 이 시계에서만 크면 그 신호가 native a11y 풍부 앱에서 추가 머지 (대부분 false positive 가능성), 메가커피에서 작으면 webview 에서는 기여 거의 없음. 반대 경우면 webview-specific 신호. L1_authoritative 의 marginal 이 ≈ 0 이면 폴백이 사실상 작동 안 함 (멘토 우려 검증).

핵심 발견 — Auto ground truth (44쌍, 결정성 신호) 에서 L1/L2/L1_authoritative 가 precision/recall 1.0 perfect. L3 와 L1+L2+L3 union 은 FP 16건 (precision 0.6) — union 이 더 나쁨. Human C (사람 라벨 8쌍) 에서는 L1 이 모든 SAME 놓침 (recall 0%) — "view tree 동일" 신호가 "사용자 입장 같은 화면" 과 다른 신호임을 입증.

해석 가이드

  • 시계 앱 → L1_only 와 L1_authoritative 가 거의 같은 canonical 수: a11y 풍부해 L1 단독으로 충분. L2/L3 폴백이 거의 무관.
  • 메가커피 → L1_only 가 canonical 수 많음 (압축률 낮음): webview 익명 view 흔들림으로 같은 화면이 여러 canonical 로 갈림. L0 md5 / L2 보강 필요.
  • L2_only / L3_only 가 압축률 매우 높음 (예: 90%+): 혼자 작동하면 다른 화면도 함부로 머지하는 false positive 신호.
  • L1+L2+L3 union 이 L1_authoritative 보다 압축률 큼: L2/L3 의 false positive 가 추가 머지를 만든다 = 위험. precision 측정 필요 (ground_truth.py).
